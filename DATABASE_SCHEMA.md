# HomeFit — Database Schema

Status: **schema v3 implemented.** v1 added the profile and assessment, v2 added the workout engine, and v3
adds the nutrition engine (food log, meal plans, saved plans and grocery checklist). Foreign keys are enabled
on every open and timestamps are normalised to UTC by the mappers. Every migration so far only *creates*
tables, so an upgrade can never rewrite or delete existing rows.

Schema changes must bump `schemaVersion`, ship a migration step, add a migration test against a database
created at the previous version, and update this file in the same commit.

---

## Policy

- **Engine:** Drift over SQLite (bundled native SQLite, no server, works in airplane mode).
- **IDs:** stable `TEXT` identifiers generated by the app. Bundled foods and recipes use fixed lowercase
  slugs (`roti-whole-wheat`, `moong-dal-khichhi`…), so logs and plans keep pointing at the same content
  across releases even if a display name is edited. User rows use a prefix + timestamp + sequence
  (`log-…`, `plan-…`, `saved-plan-…`, `grocery-…`).
- **Foreign keys:** `PRAGMA foreign_keys = ON` on every open. Cascades are used only where a child cannot
  outlive its parent (assessment → profile, saved plan item → saved plan).
- **Times:** stored as UTC `INTEGER` (seconds/milliseconds per Drift) and converted at the presentation edge.
  Nutrition **days** are different: they are stored as local `yyyy-MM-dd` text, not instants, so a meal eaten
  at 23:55 stays on that calendar day after midnight.
- **Units:** every nutrition quantity stores its unit explicitly (`g`, `ml`, `serving`). Nutrition totals are
  stored as real values and only rounded for display.
- **Migrations:** additive per version, tested against a real temporary file database. No drop-and-recreate
  of user tables and no destructive reset.

## v1 — profile and baseline assessment

| Table | Columns |
| --- | --- |
| `profile_rows` | `id` (`primary`), `age`, `height_cm`, `weight_kg`, `experience_level`, `goals` (JSON names), `priorities` (JSON), `equipment` (JSON), `session_minutes`, `training_time`, `diet_pattern`, `diet_restrictions` (JSON), `sleep_pattern`, `notifications_enabled`, `created_at`, `updated_at` |
| `assessment_rows` | `id`, `profile_id` → `profile_rows` (**cascade**), `push_ups?`, `knee_push_ups?`, `plank_seconds?`, `pull_ups?`, `squats?`, `notes?`, `recorded_at` |

Enum-backed columns store the Dart enum `name`; list columns store JSON arrays of names. Unknown stored
names fall back to a safe default instead of throwing, so older data stays readable.

## v2 — workout engine

Three additive tables created by the v1 → v2 migration; no existing column changed.

| Table | Columns |
| --- | --- |
| `workout_session_rows` | `id`, `template_id`, `template_name`, `mode`, `status`, `started_at`, `ended_at?`, `planned_minutes`, `perceived_effort?`, `is_paused`, `rest_ends_at?`, `rest_remaining_seconds?`, `last_activity_at` |
| `workout_session_exercise_rows` | `id`, `session_id` → `workout_session_rows` (**cascade**), `exercise_id`, `order_index`, `planned_sets`, `target_reps?`, `target_seconds?`, `rest_seconds`, `skipped`, `completed_at?` |
| `workout_set_rows` | `id`, `session_id` → `workout_session_rows` (**cascade**), `session_exercise_id` → `workout_session_exercise_rows` (**cascade**), `exercise_id`, `set_index`, `target_reps?`, `actual_reps?`, `target_seconds?`, `actual_seconds?`, `rest_seconds_taken?`, `skipped`, `completed_at` |

- `status` is stored by name: `inProgress`, `completed`, `abandoned`, `interrupted`. Only `completed` counts
  as a workout.
- `mode` is stored by name: `normal`, `quick`, `recovery`, `targeted`, `skill`.
- `rest_ends_at` is an absolute UTC instant, not a countdown, so rest survives backgrounding and process
  restarts. While paused, `rest_remaining_seconds` holds the frozen remainder and `rest_ends_at` is null.
- `exercise_id` has no foreign key: exercises are const Dart data with immutable slugs.
- The plan is copied into the session at start time, so editing a template later cannot rewrite history.

## v3 — nutrition engine (M5)

Five additive tables created by the v2 → v3 migration. Nothing is altered, reset or deleted.

| Table | Columns |
| --- | --- |
| `food_log_rows` | `id`, `date_key`, `slot`, `food_id`, `food_name`, `amount`, `unit`, `serving_label?`, `kcal`, `protein_g`, `carbs_g`, `fat_g`, `logged_at` |
| `meal_plan_item_rows` | `id`, `date_key`, `slot`, `kind`, `source_id`, `name`, `amount`, `unit`, `serving_label?`, `order_index`, `created_at` |
| `saved_meal_plan_rows` | `id`, `name`, `created_at`, `updated_at` |
| `saved_meal_plan_item_rows` | `id`, `plan_id` → `saved_meal_plan_rows` (**cascade**), `slot`, `kind`, `source_id`, `name`, `amount`, `unit`, `serving_label?`, `order_index` |
| `grocery_item_rows` | `id`, `name`, `food_id?`, `amount?`, `unit?`, `checked`, `source`, `created_at?` |

Design notes:

- **Planned meals and actual logs are separate tables on purpose.** Replacing a day's plan cannot touch what
  was recorded as eaten, and logging food never changes a plan. Both are keyed by `date_key`.
- **`food_log_rows` stores a nutrition snapshot** (`kcal`, macros) alongside `food_id`. Fixing a catalogue
  value later must not rewrite a past day; the id stays so the entry can still be recognised and edited.
- `slot` is stored by name: `breakfast`, `lunch`, `snack`, `dinner`, `extraSnack`. `kind` is `food` or
  `recipe`; `source_id` is the bundled slug. **No foreign key** for either, because the catalogue is const
  Dart (same reasoning as exercises).
- `unit` is `g`, `ml` or `serving`; `amount` is grams/millilitres for food and servings for a recipe.
  `serving_label` keeps the household portion ("1 roti", "1 katori") so a plan or log still reads naturally
  after the number is edited.
- **Saved plans are templates**, not day rows: `saved_meal_plan_item_rows` has no `date_key`. Loading a plan
  recreates fresh item ids on the target day, so two copies can coexist and history stays unambiguous.
- `grocery_item_rows.source` is `plan` or `manual`. Regenerating from a plan replaces only `plan` lines and
  preserves their `checked` state; manual lines are kept as they are. Nothing is ever auto-checked.
- `checked` defaults to `false`. The checklist is intentionally independent of the plan's existence: a
  deleted plan does not silently empty the shopping list.

### Migration v2 → v3

```dart
onUpgrade: (Migrator migrator, int from, int to) async {
  if (from < 2) { ... v2 tables ... }
  if (from < 3) {
    await migrator.createTable(foodLogRows);
    await migrator.createTable(mealPlanItemRows);
    await migrator.createTable(savedMealPlanRows);
    await migrator.createTable(savedMealPlanItemRows);
    await migrator.createTable(groceryItemRows);
  }
}
```

Covered by `test/features/nutrition/nutrition_migration_test.dart`, which writes a profile and a workout
session to a **real temporary file database**, drops only the v3 tables and sets `user_version = 2`, reopens
through the normal migration and asserts the profile, workout history and new nutrition tables all work.
No test and no app path clears an existing database.

## Bundled catalogues stay in code

Foods (55) and recipes (13) are const Dart in `lib/features/nutrition/data/catalog/`, not seeded tables.
The catalogue is complete at compile time, needs no loader, cannot fail offline and can be asserted in plain
unit tests. Each `FoodItem` carries its per-100 nutrition, household serving presets, state (raw / cooked /
prepared), unit and a source/estimate note; each `Recipe` stores ingredient quantities for its stated servings
and computes nutrition from the same food entries, so a recipe can never quote numbers that disagree with its
ingredients. Moving these into SQL is deferred until a query needs it (as with exercises).

## Relationships

```
profile_rows 1—* assessment_rows                       (cascade)
workout_session_rows 1—* workout_session_exercise_rows (cascade)
workout_session_rows 1—* workout_set_rows              (cascade)
saved_meal_plan_rows 1—* saved_meal_plan_item_rows     (cascade)
food_log_rows, meal_plan_item_rows, grocery_item_rows  — no foreign keys to the catalogue
```

## Safe deletion

- Bundled foods and recipes are immutable slugs; history references them without a foreign key.
- Deleting a saved meal plan removes its items through the foreign-key cascade.
- Deleting a logged entry removes only that row.
- Clearing the grocery list is an explicit confirmed action.
- Workout sessions delete with their exercises and sets; a completed session requires confirmation in the UI.
- There is still no profile reset or "delete all data" action in the app (see known limitations).

## Not implemented yet

The following remain design targets for later milestones and have **no tables** in this build: reminders and
notification events (M6), weight/measurement/photo progress and the Body Goal Timeline (M7), imported plans,
achievements, XP, backup metadata (M9), and any account or sync tables (explicitly out of scope).
