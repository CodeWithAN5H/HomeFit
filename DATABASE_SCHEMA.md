# HomeFit — Database Schema

Status: **design only — no database exists yet.** This document is the agreed target for M2. It will be
updated in the same commit as any schema change, together with the migration.

---

## Policy

- **Engine:** Drift over SQLite (bundled native SQLite, no server, works in airplane mode).
- **IDs:** stable `TEXT` identifiers generated by the app (UUID v4 for user rows, fixed slugs for bundled
  content such as `push_up_standard`). Content IDs never change across releases, so user history keeps
  pointing at the right exercise even if its display name is edited.
- **Foreign keys:** `PRAGMA foreign_keys = ON` on every open. Deletes that would break history are blocked
  by design (see *Safe deletion*).
- **Times:** stored as UTC `INTEGER` (milliseconds since epoch) or ISO-8601 `TEXT` for date-only values,
  converted at the presentation edge using the injected `Clock`.
- **Migrations:** `schemaVersion` increments with a written `MigrationStrategy` step per version, tested
  against a database created at the previous version. No drop-and-recreate of user tables.
- **Units:** every nutrition value stores its unit explicitly (`g`, `ml`, `kcal`, `mg`). Values sourced from
  a reference are marked `source` and `isApproximate`, because household portions and cooked weights vary.

## Core tables

### Profile and preferences

| Table | Key columns |
| --- | --- |
| `user_profile` | `id`, `age`, `height_cm`, `weight_kg`, `experience_level`, `primary_goals` (json), `equipment` (json), `diet_type`, `diet_restrictions` (json), `food_preferences` (json), `session_minutes`, `preferred_time_of_day`, `sleep_habit`, `created_at`, `updated_at` |
| `user_preferences` | `id`, `coaching_style` (`strict`/`friendly`/`balanced`), `gamification_enabled`, `quiet_hours_start`, `quiet_hours_end`, `units`, `theme_mode`, `restart_threshold_days` |
| `notification_preference` | `category` (`workout`, `breakfast`, `lunch`, `dinner`, `hydration`, `sleep`, `recovery`, `weekly_weight`), `enabled`, `time_of_day`, `days_of_week`, `max_repeats`, `vibration` |
| `reminder_event` | `id`, `category`, `scheduled_for`, `fired_at`, `dismissed_at`, `outcome` (`completed`, `postponed`, `ignored`) — used to avoid endless repeated reminders |

`experience_level` is descriptive only; training targets come from assessment results, never from age or
an assumed ability.

### Exercise content

| Table | Key columns |
| --- | --- |
| `exercise` | `id`, `name`, `category`, `difficulty` (1–5), `primary_muscles` (json), `secondary_muscles` (json), `equipment` (json), `is_unilateral`, `movement_pattern`, `progression_of`, `regression_of` |
| `exercise_instruction` | `exercise_id`, `locale`, `description`, `starting_position`, `execution_steps` (json), `breathing`, `common_mistakes` (json), `safety_notes`, `easier_alternatives` (json), `harder_alternatives` (json) |
| `exercise_media` | `id`, `exercise_id`, `type` (`svg`/`png`/`lottie`), `asset_path`, `frame_count`, `license`, `attribution` |

Media are **original or appropriately licensed** bundled assets referenced by relative asset paths.
No external video service is required for instructions. Optional online links are stored separately and
never load-bearing.

### Plans and training

| Table | Key columns |
| --- | --- |
| `workout_plan` | `id`, `name`, `source` (`builtin`/`imported`/`generated`), `goal`, `days_per_week`, `is_active`, `schema_version`, `created_at` |
| `workout_day` | `id`, `plan_id` → `workout_plan`, `day_index`, `focus`, `kind` (`strength`/`recovery`/`skill`/`light`) |
| `workout_exercise` | `id`, `day_id` → `workout_day`, `exercise_id` → `exercise`, `order_index`, `target_sets`, `target_reps_min`, `target_reps_max`, `target_seconds`, `rest_seconds`, `notes` |
| `workout_session` | `id`, `plan_id?`, `day_id?`, `mode` (`scheduled`/`quick`/`recovery`/`targeted`/`skill`), `started_at`, `ended_at`, `status` (`in_progress`/`completed`/`cancelled`), `perceived_effort`, `soreness_before`, `sleep_hours`, `postpone_reason`, `notes` |
| `set_record` | `id`, `session_id` → `workout_session`, `exercise_id` → `exercise`, `set_index`, `target_reps`, `actual_reps`, `duration_seconds`, `weight_kg?`, `rest_taken_seconds`, `completed_at`, `skipped` |
| `recovery_record` | `id`, `date`, `sleep_hours`, `soreness_level`, `energy_level`, `resting_feel`, `notes` |
| `personal_record` | `exercise_id`, `metric` (`reps`/`seconds`), `value`, `achieved_at`, `set_record_id` |

Set records are written as sets complete, so a killed process loses at most the in-flight set. `mode`
separates quick/recovery sessions from scheduled strength work in all statistics.

### Nutrition

| Table | Key columns |
| --- | --- |
| `food_item` | `id`, `name`, `category`, `per_100g_kcal`, `per_100g_protein_g`, `carbs_g`, `fat_g`, `fiber_g`, `source`, `is_approximate`, `household_portions` (json: label → grams), `is_vegetarian`, `contains_egg`, `common_household_item` |
| `ingredient` | `id`, `name`, `food_item_id?`, `unit`, `approx_cost_per_100g?`, `cost_source?` |
| `recipe` | `id`, `name`, `meal_slot` (`breakfast`/`lunch`/`snack`/`dinner`), `servings`, `prep_minutes`, `instructions` (json steps), `tags` (json), `is_vegetarian`, `contains_egg`, `estimated_kcal`, `estimated_protein_g`, `cost_estimate?` |
| `recipe_ingredient` | `recipe_id`, `ingredient_id`, `quantity`, `unit`, `optional` |
| `meal_plan` | `id`, `date`, `slot`, `recipe_id`, `status` (`planned`/`eaten`/`replaced`/`skipped`), `portion_multiplier` |
| `food_log` | `id`, `date`, `slot`, `food_item_id?`, `recipe_id?`, `portion_label?`, `grams?`, `millilitres?`, `kcal`, `protein_g`, `carbs_g`, `fat_g`, `logged_at`, `entry_mode` (`portion`/`grams`/`recipe`/`quick`) |
| `grocery_item` | `id`, `name`, `quantity`, `unit`, `checked`, `source_meal_plan_ids` (json), `estimated_cost?` |

Nutrition figures carry `source` and `is_approximate`; no invented precision. Costs appear only where a
reliable, user-editable estimate exists, and are labelled as estimates.

### Progress

| Table | Key columns |
| --- | --- |
| `weight_entry` | `id`, `date`, `weight_kg`, `note`, `measured_at` |
| `body_measurement` | `id`, `date`, `chest_cm`, `waist_cm`, `hips_cm`, `left_arm_cm`, `right_arm_cm`, `left_thigh_cm`, `right_thigh_cm`, `notes` |
| `progress_photo` | `id`, `date`, `angle` (`front`/`side`/`back`), `file_path` (app-private), `consent_given`, `created_at` |
| `goal_target` | `id`, `goal_type` (`weight`/`strength`/`muscle`/`physique`/`skill`), `target_value?`, `target_date?`, `is_active`, `updated_at` |

four new weight entries or two completed weeks), so the Body Goal Timeline does not jitter daily.

## Relationships (summary)

```
user_profile 1—1 user_preferences
workout_plan 1—* workout_day 1—* workout_exercise *—1 exercise 1—* exercise_instruction
workout_session 1—* set_record *—1 exercise
recipe 1—* recipe_ingredient *—1 ingredient
meal_plan *—1 recipe
food_log *—1 food_item | recipe
goal_target 1—* goal_estimate
```

## Safe deletion

- Exercises and recipes referenced by history are **archived**, not deleted.
- A completed session may be deleted only with explicit confirmation; its set records cascade.
- Progress photos are deleted from disk *and* database on request, immediately and without a "trash" copy.
- Profile reset is a distinct, confirmed action that clears personal rows while leaving bundled content.

## Backup format

A versioned JSON document: `{ "format": "homefit-backup", "schema_version": N, "app_version": "...",
"created_at": "...", "includes_photos": false, "tables": { ... } }`. Import validates the format and
schema version, computes a per-table diff, and shows the consequences before anything is written.
Photos are excluded unless the user explicitly includes them; nothing is uploaded anywhere.
